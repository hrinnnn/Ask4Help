## 每个 stage 的固定步骤

1. 冻结 ID/OOD 条件、seeds、oracle 与 base checkpoint；确认 oracle 在 ID 和当前 OOD 上成功率均达到任务门槛，且 base policy 已掌握 ID、在当前 OOD 上存在受控缺口。
2. 跑纯 policy rollouts，完成 failure-detection comparison。
3. 对每个 gated 方法，从同一 base policy 运行冻结的 ID/当前 OOD 严格交替 deployment stream，直到自然得到 100 条成功且发生真实接管的 expert trajectories；不设 accepted-ID/accepted-OOD 配额。Internal-Feature PCA、Diff-DAgger、Failure-Recovery 分别形成独立且应显著 OOD-dominant 的数据；Offline BC 直接收集当前 stage 的完整 OOD oracle demonstrations。不得只完成其中一组。
4. 审计四份数据的动作、状态、视频、触发区间和 temporal-mask 边界，再按专家低层动作数选择共同预算。
5. 四组分别使用原始 ID + 本组 OOD expert 数据，从同一 base checkpoint 独立训练；不得让一组数据混入另一组。
6. 按《训练与持续运行协议》保存并评测共同训练节点；不得为不同方法分别挑选最佳 step。
7. 在相同固定 ID/OOD seeds 上评测四个更新后策略的 Success Rate；mixed ID/OOD stream 另用于评价实际数据选择。
8. 更新结果索引，逐组写明 collection、training、evaluation 路径、完成标记、成功定义和已知限制。

因此，一个 stage 的完成产物至少包括：`1` 个共同 base checkpoint、`4` 份 OOD expert datasets、
`4` 个独立更新后 policy 以及 `4` 组共同 ID/OOD evaluation。若任务含三个 OOD stages，则方法比较
部分原则上对应 `12` 份 stage-method 数据、`12` 个更新后 policy 和相应评测。受控四时机 sweep
另按《Takeover Timing Sweep》执行，不计入这四个方法分支。

Gated collection 的 `100` 是每个 stage-method 的 accepted 总量，不是每个 split 各 50 条。
Internal-Feature PCA 默认要求 OOD accepted 占比至少 80%；低于该门槛不得进入训练。Diff 与
Failure-Recovery 保留自然比例，但若 accepted ID 接近或超过 OOD，同样应先按《共享实验协议》审计。
训练公平性通过采集后的共同 expert-action budget 实现，不能通过改变采集分布实现。

Timing sweep 的条件、DCA/EAS/DCE 和启动门槛统一记录在对应子计划中，不在单个任务里另行修改。

## Agent 接力规则

1. 新 Agent 先按 `AGENTS.md` 顺序读完实验管理文档，再检查服务器上的实际完成标记。
2. 从总计划中选择第一个未完成且依赖已满足的任务。若显示 `未登记，认领前核实`，先核实没有现存负责人、总控或后台进程；若显示 `未认领`，仍需快速检查实际完成标记。确认后先写入认领信息，再开始任何实现或服务器操作。
3. 已认领任务不得重复执行。需要接管时先核实原 Agent、PID、总控状态、日志和完成标记，再把认领改为 `已接管`。
4. 复用共享协议；模型专属参数以该任务的脚本和 manifest 为准。
5. smoke 通过后由持久化总控程序自动执行同一任务内的收集、训练和评测，无需逐阶段重复询问；心跳只监督和恢复总控，不以单个阶段结束为完成。
6. 只有任务定义、指标定义或预算需要改变时才暂停请求确认；一般运行错误应先诊断和恢复。
7. 每完成一个阶段，立即更新本文件状态和《结果索引》，再继续下一阶段；整项任务结束或释放时同步清理认领信息。

若一个总计划条目包含多个可独立并行的子任务，先在对应子计划中拆出子任务认领表，再按最小独立单元认领；不得用一个宽泛的父任务认领阻塞所有并行工作，也不得在没有子任务登记时多人同时修改同一条 pipeline。
