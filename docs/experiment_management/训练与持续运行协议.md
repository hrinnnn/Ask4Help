# 训练与持续运行协议

本文规定所有正式 VLA 行为克隆训练的样本边界、checkpoint 选择和无人值守执行方式。任务专属计划可以覆盖训练步数与评测频率，但必须在启动前写明，不能根据最终测试结果事后修改。

## 1. 强制 Temporal Mask

每个 episode 的每一个真实 observation 都必须成为训练 anchor，包括最后 `action_horizon - 1` 个 observation。禁止为了获得完整 action chunk 而过滤 episode 尾部。

对于从 anchor 开始不足 `action_horizon` 的 target：

1. 保留全部真实 action；
2. 用最后一个真实 action 补齐固定长度，仅用于保持张量形状；
3. 同时生成 temporal validity mask；
4. loss 只在真实 action timestep 和真实 action dimension 上归约，padding 不得进入分子或分母。

以 horizon 10 为例，最后一个 observation 必须产生 1 个有效 target 和 9 个 masked target；倒数第十到最后一个 anchor 的有效长度应依次为 10 到 1。

### 已核实实现

- 本仓库参考实现：`tools/xvla_stackcube_temporal_mask.py`。
- 边界测试：`tests/test_xvla_stackcube_temporal_mask.py`，覆盖最终 anchor、全部 anchor、padding loss 和 dummy action dimensions。
- 2026-08-13 使用 RLinf 环境运行上述测试，结果为 `4 passed`。
- 5090 上当前 X-VLA 数据入口 `datasets/domain_handler/panda_airplane.py` 已输出 `action_valid_mask`；`models/action_hub.py` 已在 loss 中应用该 mask；`train.py` 会记录 mask coverage。

5090 上这部分 X-VLA 改动目前是服务器工作区修改，不应被视为可复现来源。下一次正式训练前，必须先把实际使用的修改整理到本地 GitHub 源码，并从服务器重新拉取；不得只依赖服务器上的未提交文件。

### 正式训练启动门槛

每个新数据集在正式训练前必须保存并检查：

- episode 数与总 anchor 数；
- tail-anchor 数；
- 有效 target 数量 1 到 `action_horizon` 的分布；
- 最后一个 observation 是否保留且只有 1 个有效 target；
- 2-step 训练、checkpoint reload 和一次有限值 forward。

## 2. 训练步数与 Checkpoint

- 默认最大训练步数为 **10,000 steps**，每 **500 steps** 保存 checkpoint。
- 默认在 2k、4k、6k、8k、10k 做 checkpoint-selection evaluation。
- 如果一次正式评测代价明显过高，任务计划可以在启动前改为 3k、6k、9k、10k；同一组比较中不得临时改变频率。
- 所有中间 checkpoint 都保留。即使继续训练，较早 checkpoint 的有效结果也不能被后续训练覆盖。
- checkpoint selection 使用冻结的 validation seeds；论文最终 test seeds 必须独立，并只在 checkpoint 选定后使用。
- loss 只用于训练健康检查，不能替代任务 Success Rate，也不能单独作为停止条件。

## 3. ID Base Policy 停止规则

ID policy 的目标是得到一个已掌握 ID、但仍可在 OOD 上暴露能力缺口的基础策略。

1. 按冻结的 checkpoint-selection seeds 在每个评测节点运行 ID evaluation。
2. 最早达到 **ID Success Rate >= 80%** 的 checkpoint 成为候选停止点。
3. 使用独立且规模更大的 ID validation seeds 确认达到 80% 后，可以停止训练并冻结该 checkpoint。
4. 若到 10k 仍未达到 80%，不得悄悄放宽任务、成功定义或阈值；保留所有结果并报告 base policy 未通过验收。

## 4. OOD 更新实验停止规则

对 Internal PCA、Diff-DAgger、Failure-Recovery 和 Offline BC 等 matched-budget 对照：

- 所有方法必须从同一 base checkpoint 开始，在相同训练步数节点、相同 OOD validation seeds 上评测。
- 不允许某个方法在 2k、另一个方法在 6k，再把各自最高点放入同一主表。
- 默认继续到 10k。若希望根据“基线已经形成清晰区分”提前停止，必须在任务计划中提前冻结判据。
- 在没有任务专属判据时，默认可操作判据为：固定验证集上最优与最差方法的 OOD Success Rate 相差至少 15 个百分点，且结果不是所有方法都接近 0% 或 100%。满足后可把该共同训练步数作为候选停止点，并用独立 validation seeds 复核。
- 若判据未满足或排序不稳定，继续训练到下一评测节点；10k 为默认上限。

这里的早停只决定是否继续消耗训练资源，不改变 matched expert-action budget、数据版本、成功定义或最终评测协议。

## 5. 持久化多阶段执行

长实验必须由一个可恢复的**总控程序**负责阶段推进，而不是把阶段推进寄托在单次心跳上。总控程序至少覆盖：

`runtime selection/setup -> smoke -> collection -> data audit -> training -> checkpoint evaluation -> final evaluation -> result registration`

对 X-VLA，`runtime selection/setup` 先检查 5090 的实际空闲资源；没有足够卡时必须按《环境与存储》自动转入阿里云环境恢复和 smoke，而不是把任务标记为 blocked 或等待下一次心跳。

总控程序应：

- 在后台持久运行，记录 PID、日志、当前阶段和输出根目录；
- 使用 `pipeline_state.json` 或等价状态文件记录已完成阶段；
- 每个阶段写独立完成标记，整条链路只在 `PIPELINE_COMPLETE` 出现后结束；
- 重启时跳过已验收阶段，从第一个未完成阶段继续；
- 遇到 partial output 时先诊断，使用新的 retry 目录恢复，禁止覆盖旧产物；
- 在一个阶段完成后立即启动并验证下一阶段，而不是退出等待下一次人工指令。

心跳任务只承担三件事：检查总控进程是否存活、检查当前阶段是否持续推进、在总控异常退出时诊断并从状态文件恢复。**一次阶段成功不是心跳任务的完成条件；只有 `PIPELINE_COMPLETE`、确实需要用户决策或无法自动恢复的错误才允许停止。**

若某项实验尚无总控程序，正式启动前应先补一个最小总控入口。若只能由心跳直接管理阶段，则心跳指令必须列出完整阶段图，并在同一次唤醒中从已完成阶段推进到下一阶段，不能只汇报状态。

## 6. 当前 Stage-2 实现状态

`tools/run_xvla_stackcube_stage2_pipeline.py` 已对齐《X-VLA StackCube 目标位置 OOD 与受控介入计划》的四个 timing condition，并覆盖 oracle 验收、共同 cohort、完整 suffix 预算、temporal-mask smoke、10k 训练、共同 checkpoint selection 和最终 100 ID/100 OOD 评测。流程以名义预算 `B=2002` 为上限，并在共同成功 seed 集合上解析出不超过该上限的最大共同可达完整 suffix 预算；不得截断 episode，也不得因为预算不可达而静默启动不匹配的训练。
