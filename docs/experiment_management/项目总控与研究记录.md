## 1. 项目主线

当前论文的核心不是“再跑几个成功率”，而是回答一个更具体的问题：

> Robot-gated DAgger 需要在两个层面做出正确的数据采集决策：先决定哪些 rollout 值得请求专家，再决定在 rollout 的哪个状态开始接管。接管时机决定了专家数据是冗余的完整示范、直接完成任务的短 suffix，还是失败后的恢复轨迹。

因此，所有正式实验都要围绕以下链路组织：

`可靠任务与 base policy -> data selection -> takeover timing -> expert data -> matched-budget policy update -> ID/OOD evaluation`

Internal-feature PCA 是一个可部署的 gate 和 timing proxy，但它不能替代任务设计、时机对照或下游学习验证。论文中应把 PCA 的结果放在这条因果链上解释，而不是把单独的 detector AUPRC 当成整项工作的结论。

## 3. 正式实验的不可变规则

### 3.1 任务和数据

- 每个 stage 先冻结任务语义、ID/OOD 因素、阶段 predicate、reset invariant、Oracle success 定义和 seed manifest。
- ID policy 只用 ID demonstrations 训练；不能用旧几何任务的 checkpoint 代替新任务 base。
- OOD 必须仍然可由 Oracle 完成。Oracle 失败说明任务设计无效，不说明 policy 的 OOD 泛化失败。
- mixed-stream gated collection 使用严格交替的原始 ID/OOD attempts；不设置 accepted 50/50 配额，也不为了凑比例专门补 ID。
- Internal-feature PCA 的 accepted 轨迹应自然 OOD-dominant；若接近均分，先审计 base ID/OOD SR、Oracle、calibration、threshold、norm、split 和 trigger，再决定是否停闸。
- 多阶段任务只训练一个 ID base；OOD1、OOD2、OOD3 必须从同一个 immutable ID base 独立收集、独立训练、独立评估，不混合、不串行续训。
- timing sweep 是 OOD-only，用于隔离接管时机；不能用 mixed-stream collection 代替 timing sweep。

### 3.2 训练和边界

- 所有 VLA BC/SFT 必须保留每个真实 observation anchor，包括 episode 尾部 anchor。
- 跨越 episode 边界的 action chunk 可以用最后真实动作做 padding，但必须使用 temporal validity mask；padding 不得进入 loss 分母。
- 正式训练前必须报告 anchor 总数、tail-anchor 数量、mask validity 分布，并完成 2-step checkpoint reload/forward smoke。
- 四方法比较必须使用同一 ID base、同一 OOD 定义、同一专家预算、相同训练配置和 held-out seeds。
- 专家预算按真实低层 expert actions 匹配，不按轨迹条数假设公平。
- 任何 gate 的 detector 评测都必须是 passive：评测时不让 detector 改变 rollout 动作；阈值只由独立成功 ID calibration 得到。

## 4. Agent 分工和认领规则

### 4.1 总控模式：目标授权，而不是逐条遥控

总控只下达四类信息：目标、不可违反的科学约束、完成定义和需要回报的证据。Agent 自主决定具体命令、代码组织、诊断顺序和资源安排，并对自己的执行结果负责。

- Agent 可以自主选择合理的修复方案、补充 smoke、调整等待和监测节奏。
- Agent 可以在当前实验目标内自行处理路径、依赖、视频落盘、进程恢复等工程问题。
- Agent 发现结果不符合预期时，应先自主提出原因排序和下一步实验，而不是停在简单汇报。
- Agent 不得自行改变任务语义、success predicate、ID/OOD 定义、专家预算口径或把 diagnostic 结果升级为 canonical。
- 只有涉及研究假设、共享 geometry、跨 Agent 资源冲突、正式结果纳入主表或不可逆的大规模资源消耗时，才需要总控介入。

每次回报重点回答四件事：现在处于哪个阶段、证据说明什么、下一步准备自主做什么、什么条件会让它停下并请求总控判断。

### 项目总控（Codex）

- 负责解释实验结果是否支持论文假设，批准或拒绝阶段转换，协调 Agent，维护本文件和结果索引。
- 任何与共享 task geometry、success predicate、norm、base checkpoint 或预算相关的冲突，由总控裁决。
- 不因为一个中间进程结束就宣布整条 pipeline 完成；必须验收当前产物并推进已批准的下一阶段。

### StackPyramid timing Agent

- 是 StackPyramid v4 geometry、Oracle、stage predicate 和 timing gate 的唯一 owner。
- 在 full gate 结束前可以修复实现问题，但每次修复必须说明一个根因、一个最小改动和一个针对性 smoke。
- 一旦 full gate 开始，不再继续漂移几何；只允许修复会阻止复现的工程错误。
- 完成后必须发布：源码 commit、task spec、seed manifest、Oracle gate report、ID collection/norm、immutable ID base、base/prefix gate report。

### StackPyramid 四方法 Agent

- 在 Timing Agent 发布唯一冻结资料前保持 blocked，不改 geometry，不运行自己的 v4，不使用 v3 或候选版本。
- 解锁后原样复用唯一 v4 source，分别完成 Internal PCA、Diff-DAgger、Failure-Recovery、Offline BC 四组；四组独立但共享协议。
- 任何一组门禁失败时保留 diagnostic，不能用 retry 配额掩盖问题。

### OpenDrawer Agent

- 只负责当前独立 ID-base controller；先满足 ID gate，再进入 OOD collection 和 matched-budget update。
- 到达一个评测 checkpoint 后，先核对 summary 和视频数量，再决定是否进入下一步；不能仅凭 loss 或 checkpoint 文件存在宣布通过。

## 5. 每次唤醒的总控流程

每次 30 分钟检查不是重复报数，而是按以下顺序做判断：

1. 读取三个 Agent 的最新实际响应、PID/控制器状态和当前阶段 marker。
2. 对照本文件、`共享实验协议.md`、对应 plan 和实验总计划，确认 Agent 没有越过依赖门。
3. 若长任务稳定：只检查真实吞吐、GPU/磁盘、最新产物和错误信号，不打断任务。
4. 若出现错误：先判断是环境/路径/代码问题还是科学门禁失败；可恢复的工程问题立即修复，科学门禁失败则停在当前阶段并保留证据。
5. 若阶段完成：审计 summary、分母、视频/动作边界、配置 provenance；通过后在同一次唤醒中启动并验证已批准的下一阶段。
6. 更新本文件的状态和研究日志；只有发生实质进展、修复、阶段转换或需要用户决策时才向用户报告。

监测节奏：启动、恢复、阶段切换和接近门禁时 5--10 分钟；确认稳定的小时级训练/收集/评测后 20--30 分钟。短 smoke、import、静态审计不建立监测任务，直接完成并判定。

## 6. 采用的 AutoResearch 工作方式

这里借鉴 AutoResearch 的“固定评估器 + 单变量迭代 + 机器可读结果 + 保留/回退”思想，但不把研究变成盲目搜索：

- 每个阶段必须有明确目标、约束、通过条件、输出目录和停止条件。
- 每轮只处理一个可解释的假设；先写证据，再改动；改动后做针对性验证。
- evaluator 必须输出 `pass/fail`、关键分数、分母、配置版本和证据路径。
- 只有 verifier 通过后才允许把结果推进到下一阶段；失败产物保留为 diagnostic，不覆盖旧结果。
- 任何“修复”如果改变 task geometry、success predicate、数据来源或训练口径，必须重新走前置 gate，不能当作普通 bug fix 混入主结果。
